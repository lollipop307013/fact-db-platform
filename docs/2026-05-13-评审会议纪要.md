## 二、决策事项

### 1. 入库的两条数据来源（已对齐）

| 来源 | 数据形态 | 处理方式 |
|---|---|---|
| **基于实体整理的内容**（如 EB 实体表+相关信息） | 实体基础信息 + 关联描述 | 实体基础信息直接入库；相关信息进 LLM 抽取事实，强制关联到原实体 |
| **基于纯文本** | 长文本无关联实体 | 抽取出来的实体可能是新的，也可能命中库内已有实体（不强制关联到任何固定实体） |

两者本质都走 LLM 抽取，差异仅在于"是否强制关联到一个固定实体"。

### 2. 批量导入模板分两类（重要）

兆伟提出：项目侧（如运营）有结构化的活动数据需要批量导入（活动名、时间、描述等），希望直接以模板形式导入。

**最终方案**：

| 模板类型 | 内容 | 是否抽取 | 是否走审核 |
|---|---|---|---|
| **仅基础字段**（前 N 列） | 实体名、事件名、时间等结构化字段 | ❌ 不抽取 | ❌ 直接入库 |
| **基础字段 + 相关信息列** | 多一列"相关信息"长文本 | ✅ 走 LLM 抽取 | ✅ 走审核 |

**具体规则**：
- 模板字段对所有 Tab 一致（实体/事件/事实通用）
- **由前端在导入入口判断走哪条路径**（不交给后端语言判断，避免不准）
- 在管理 Tab（实体/事件/事实）导入时，模板**只读前 N 列**（基础字段，直接入库）
- 在"提取审核"页导入时，**支持完整模板**（含"相关信息"列，走 LLM 抽取）

### 3. 批量导入入口的两条路径（保留并行）

> ⚠️ 此处会议有讨论到"是否收拢到 ExtractTab"，但**结论是保留两条路径**——项目侧（运营）有直接结构化数据导入需求，不能强制走抽取审核。

**两条路径并存**：

| 入口 | 模板 | 处理逻辑 |
|---|---|---|
| **管理 Tab（实体/事件/事实）的"批量导入"** | 仅基础字段（前 N 列） | 不抽取，直接入库 |
| **ExtractTab 的"文件导入"** | 完整模板（含"相关信息"列）/ 长文档 | 走 LLM 抽取 → 进审核区 |

**模板字段对所有入口一致**（同一份模板）：
- 在管理 Tab 入口，前端**只读取前 N 列基础字段**，"相关信息"列被忽略
- 在 ExtractTab 入口，前端读取完整模板，把"相关信息"列丢进 LLM 抽取
- 由前端在两个入口分别处理读取逻辑（不交给后端语言判断，避免不准）

### 4. 文件导入的异步任务交互（新增需求）

**问题**：文件导入需要 LLM 处理，耗时较长，不能像文本粘贴那样同步返回。

**最终方案**（不再额外做任务列表页）：

1. 用户上传文件 → 后端确认接收 → 右侧审核区**立即生成一个占位批次卡片**（与现有批次卡片样式一致）
2. 卡片显示：批次编号、文件名、状态"提取中…"、进度（如有）
3. **前端轮询**后端任务状态接口
4. 任务完成 → 卡片自动刷新，展示提取结果（与现有批次相同的交互）
5. 多个文件并发导入 = 多个占位卡片

**后端补接口**：陈燕栋提供"任务状态查询"接口（输入 task_id 或 batch_id，返回当前状态/进度/结果）

**文本粘贴提取**：保持同步即时返回，不需要任务管理。

### 5. 操作日志架构（前后端分工）

**问题**：批量导入是前端调后端接口触发的，前端记录不到具体哪些数据成功/失败的细节。

**最终分工**：

| 操作类型 | 触发方 | 日志记录方 |
|---|---|---|
| 平台 UI 手动单条操作（新建/编辑/状态变更等） | 前端用户操作 | **前端 jhaochen** 记录到平台 db |
| 批量导入（含批量入库的具体逐条结果） | 后端处理 | **后端陈燕栋** 记录到后端 db |

**联调方式**：
- 双方共同维护一份 db 库，或后端给前端提供日志写入接口
- 前端把"操作人 / 操作内容"等元信息透传给后端
- 后端在批量导入处理完成后写入对应日志条目
- 后端将该日志服务化（后端在 IP 8080 提供的目前是 demo 测试服务，正式上线由工程同学做工程化）

### 6. 待审核数据的临时存储（确认）

抽取得到的待审核数据**不能丢**——LLM 抽取有成本，不能因刷新页面就清空。

**结论**：由 jhaochen 这边在平台 db 临时持久化，前端从平台 db 取待审核数据展示。
