# 字段级差异校验 · 机械规则设计文档

> 适用范围：审核工作台「新旧版本对比」字段级 diff 高亮能力
> 说明：本方案为**纯代码机械规则**（无 AI 语义理解），基于文本结构（标点/换行）与字符级最长公共子序列（LCS）算法实现，目标是在不引入 AI 判断的前提下，尽量精确地告诉审核人员"改了哪里"。
> 状态：设计草案，待评审
> 关联代码：`src/cases/fact-db/review-types.ts`（`diffChars` 为本次设计过程中写的**原型/参考实现**，用于验证方案可行性、推演边界 case，并非已上线的既有能力）

---

## 一、背景与为什么需要这份规则

### 1.1 背景：事实库审核需要"新旧版本对比"能力

事实库的内容会通过内容同步增量变动、QA 新建/更新/下线、相似错误挖掘、批量导入等多种渠道产生变更，这些变更生效前都要经过人工审核。审核人员必须清楚看到"一条事实/某个字段从旧版本改成新版本，具体改了哪里"，才能快速判断改动是否合理、要不要通过——这是审核效率和准确性的刚需，不是可选的体验优化。

**现状：平台目前不具备这个能力**——无论是线上产品还是本次原型 demo（在本轮设计之前），审核工作台都只能展示新旧两个版本的完整文本，无法定位到具体变化的字/词/句，审核人员只能整段肉眼比对，效率低、容易漏判。

`src/cases/fact-db/review-types.ts` 里的 `diffChars` 是本次为了设计并验证"字段级 diff 高亮"这个**待新增能力**是否可行、探索各种边界 case 而写的原型代码，不代表既有生产能力。本文档的目的，就是在这份原型基础上，把机械规则的能力边界和实现方案定下来，作为正式开发前的设计依据。

### 1.2 原型验证中发现的问题

用原型代码实际推演后发现，纯字符级 LCS diff（把新旧两段文本当作两个字符数组，找最长公共子序列，剩下的部分标记为增/删）存在这些问题：

- **粒度虚假精确**：算法确实能标到"第几个字符"变了，但 LCS 追求的是"整体编辑距离最短"，不是"人类认为合理的对应关系"。一句话中间改了几个字，LCS 常常会在更远的地方找到偶然重复的字符去匹配，导致高亮**支离破碎、上下跳动**，反而降低可读性。
- **无法给出"结构性"结论**：审核人员真正想知道的是"哪一句话变了""是不是整句新增/删除了一句话"，而不是零散的字符补丁。
- **中文没有空格分词**，长句字符级 diff 更容易出现"错位对齐"（比如把后半句的字符匹配到前半句）。

结论：**直接对整段文本做字符级 LCS，定位不稳定、可读性差**。更可靠的思路是**先用确定性的方式圈出"差异到底发生在文本的哪个区间"（差异起点/终点），再在这个小范围内由粗到细逐级定位**——即：**先定位差异起点 → 逐段 → 逐句 → 逐字**，层层收窄范围，而不是一上来就在整段文本上做字符级匹配。这个顺序既符合"人改文档通常是从某处开始改、改到某处为止，前后大段文字不变"的直觉，也让每一级的比较范围更小、判断更确定。

## 二、机械规则能分析出的差异类型（能力边界）

### ✅ 能可靠识别的

| 差异类型 | 说明 | 判定依据 |
|---|---|---|
| **整句新增** | 新版本比旧版本多出一整个子句/句子 | 该片段在旧文本片段序列中找不到匹配 |
| **整句删除** | 旧版本的某个子句在新版本中消失 | 该片段在新文本片段序列中找不到匹配 |
| **整句修改** | 同一位置的片段前后都存在，但内容不同 | 新旧片段位置相邻对应，且内容不完全相等 |
| **片段内字符差异**（在"整句修改"基础上的二级能力） | 在已定位到"这一句变了"之后，进一步在**这一句内部**做字符级 LCS，标出具体增删的字/词 | 复用现有 `diffChars`，但作用范围收窄到单个子句，不再是整段文本 |
| **纯标点/格式差异** | 文字完全相同，仅句末标点、全半角、空格数量不同 | 片段做"标准化"（去空白、标点归一）后完全相等，但原始文本不相等 |
| **换行/分段结构差异** | 段落被拆成了不同数量的行 | 换行符作为独立片段类型参与比较 |
| **空字段 ↔ 有值** | 整个字段从空变为有值，或反之 | 片段序列长度为 0 vs >0 |
| **纯增删**（长度变化，如 `AAA`→`ACAA` 中间插入一个字符） | 即使文本中有重复字符，只要新旧长度不同（存在净增删），LCS 对"增/删了几个字、在哪个位置"的判定通常唯一确定，不会出现锚点歧义 | 实测验证：`diffChars("AAA","ACAA")` 稳定输出 `same("A")+add("C")+same("AA")`，无歧义（详见 3.3.1） |

### ⚠️ 能识别但需谨慎展示（容易产生误判/噪音）

| 差异类型 | 风险 | 处理建议 |
|---|---|---|
| **子句顺序调换（移动）** | 采用「内容多重集合匹配」（3.1）后可安全吸收：不主动声称"从位置X移动到位置Y"（避免猜错对应关系的风险），只用"内容是否仍存在"这一弱结论去抑制误判——存在则不标注，不存在才判定新增/删除 | 不展示"移动"标记，只是不再对该内容误报新增+删除；重复片段需用"消耗式配对"（按出现顺序一一对应），否则数量变化会被漏判（见3.1 步骤2） |
| **大小写 / 数字千分位等格式差异**（如 "1000" vs "1,000"） | 机械规则不理解语义等价，会判定为"变化" | 默认视为**实质变化**（不做格式归一化），如后续有需要可加白名单规则单独配置 |
| **重复/交替字符模式**（如 `AAAAA`→`ABABA`，长度不变、内容重复） | 无标点可切分，直接落到Step3 字符级 LCS；新旧长度相等时存在多种"数学等优"的对齐方案，LCS常选中偏离直觉的一种，把本该"逐位交替替换"的改动展示成整块删除+整块插入（详见 3.3.1 实测案例）。**注意与"纯增删"区分**：只有长度不变才会有此歧义，长度有变化时判定仍是唯一确定的 | 长度相等时改用「按位对齐」规则替代 LCS（见 3.3.1）；长度不等时无此问题，无需特殊处理 |

### ❌ 机械规则做不到（需要 AI 语义理解，明确排除在本方案外）

- **语义等价改写**：用了不同的词但意思相同（如"游戏正式上线"→"游戏已发布"），机械规则会判定为"变化"，无法判断是否语义等价
- **错别字修正 vs 有意的实质修改**：无法区分改动的"性质"，只能呈现"改了"这一事实
- **复杂重排**（一段话拆成两段，或两段合并成一段，且顺序打乱）：机械规则的片段匹配在这种场景下可能出现错位，只能保证"不崩、有兜底"，不保证阅读体验最优

> 结论：机械规则的目标不是"完美复原编辑意图"，而是"用确定性算法尽量缩小审核人员需要肉眼核对的范围，并保证结果可解释、不做过度猜测"。

## 三、实现方案：级联裁剪，由粗到细逐级定位

核心顺序：**Step 0 定位差异起点/终点（公共前缀/后缀裁剪） → Step 1 段落级定位 → Step 2 句子级定位 → Step 3 字符级定位**。每一级只在"上一级判定为有差异"的范围内继续往下细化，未变化的部分不再进入下一级比较——既减少计算量，也避免大范围 LCS 产生的错位匹配。

```
新旧字段文本
    │
    ▼
Step0 公共前缀/后缀裁剪 → 圈出「确定不变的头/尾」+「中间待定差异区」
    │
    ▼
Step1 差异区按段落（\n\n / \n）切分 → 逐段对比 → 标出「哪几段变了」
    │
    ▼
Step2 对「变了的段」按句子标点切分 → 逐句对比 → 标出「哪几句变了」
    │
    ▼
Step3 对「变了的句」做字符级 LCS（复用现有 diffChars）→ 精确到字的增删高亮
```

### 3.0 Step 0：定位差异起点/终点（公共前缀 / 公共后缀裁剪）

这是**最先执行、也是最关键的一步**，目的是用完全确定性的方式（不依赖 LCS 猜测对应关系）快速圈出真正需要比较的范围：

1. **从头扫描**：逐字符比较旧文本 `a` 与新文本 `b`，找到第一个不相同的位置 `i`，则 `a[0..i)` 与 `b[0..i)` 完全相同 —— 这就是**差异起点**，起点之前的内容直接标记为 `same`，不再参与后续任何比较。
2. **从尾扫描**：从两段文本末尾往前逐字符比较，找到最后一段公共内容，作为**差异终点**（终点之后的内容同样直接标记为 `same`）。
3. 裁剪后剩余的中间部分 `a[i..n-tail)` 与 `b[i..m-tail)` 才是**待定差异区**，交给 Step 1 继续处理。

> 为什么优先做这一步：公共前缀/后缀是唯一确定的（不存在"猜多个候选对应关系"的问题），计算量是 O(n)，比一上来对全文做 LCS 更快、更稳；同时天然符合"改动通常集中在文中某一段，前后大量文字不变"的编辑习惯，能直接把无关内容排除在比较范围外。

### 3.1 匹配策略：内容多重集合匹配（替代片段级 LCS，段落/句子级通用）

Step1（段落）、Step2（句子）都采用同一套匹配策略——**先按内容精确匹配 + 消耗式配对，剩下落单项再判定修改对**，而不是直接对片段序列跑 LCS。原因：LCS 要求匹配位置在两侧序列中保持单调顺序，遇到"内容整体挪了位置"的片段会被误判为"删除+新增"；内容匹配不要求顺序，能安全吸收纯移动，同时计算量从 LCS 的 `O(n·m)` 降到哈希匹配的 `O(n+m)`。

**具体步骤（对段落数组 / 句子数组通用，下面以“片段”统称）**：

1. **编号**：旧侧片段编号 `o1..on`，新侧片段编号 `n1..nm`（编号即原始顺序位置）。
2. **精确内容匹配（消耗式，按出现顺序配对，不是布尔存在性判断）**：按 `normalized` 文本分组，对每一种取值，把旧侧的出现序列与新侧的出现序列**按各自原始先后顺序一一配对**（第 1 个配第 1 个、第 2 个配第 2 个……），配对上的即为 `same`（内容未变，若位置也没变则完全无需标注；若位置变了，也不特殊标"移动"，同样不高亮，只是不再参与后续判断）。
   - 注意：这里必须是"消耗式"配对，而不是简单查"是否存在"——否则如果旧侧有 3 个相同片段、新侧只剩 2 个，布尔存在性检查会把 3 个都判定为"仍存在"，漏掉真正被删掉的那 1 个。按出现顺序配对后，旧侧配不上的第 3 个才会正确落入下一步的"落单删除"。
3. **落单项处理**：配对完成后，旧侧未配对上的片段是"落单删除候选"，新侧未配对上的是"落单新增候选"。
4. **修改对判定（复用既有规则）**：对落单候选按位置相邻 + 相似度阈值（公共子串占比 ≥ 40%，或首尾标点一致）两两比较，能配对上则判定为「修改对」，交给下一级继续细化；配对不上则是真正的整句/整段新增或删除。

### 3.2 分级应用

- **Step 1（段落级）**：对 Step 0 裁剪后的"待定差异区"，按段落分隔符（`\n\n`、`\n`）切分后，套用上面 3.1 的匹配策略，得到段落级的 `same` / 修改对 / 新增 / 删除。
- **Step 2（句子级）**：对 Step 1 判定为「修改对」的每一组新旧段落，按句子标点（`。！？；，、：` 及英文对应符号）切分为子句数组，同样套用 3.1 的匹配策略，得到句子级的 `same` / 修改对 / 新增 / 删除；未匹配到「修改对」的子句按整句新增/整句删除展示，不再细化到字符。

### 3.3 Step 3：修改句内的字符级定位

对 Step 2 判定为「修改对」的每一组新旧子句，直接复用现有 `diffChars(oldSentence, newSentence)`，得到精确到字符的增删高亮——算法本身不变，只是**输入范围从"整段文本"收窄到"一句话"**，从根本上避免长文本 LCS 的错位对齐问题。

#### 3.3.1 已知盲区：等长替换 + 重复字符会让 LCS 找错锚点

> 前提说明：以下问题**仅在新旧文本长度相等**时出现；只要长度不等（存在净增删），LCS 的判定是唯一确定的，不受重复字符影响，详见 3.3.2 的反例验证。

**问题场景**：`AAAAA` → `ABABA`（长度都是 5）。这种句子内部没有标点可切，Step0/1/2 都切不出更小片段，直接进入 Step3 的字符级 LCS。

- Step0 公共前缀/后缀裁剪：从头比较第 1 位就不同（`A` vs `A` 相同，第 2 位 `A` vs `B` 不同）→ 前缀仅 `"A"`；从尾比较同理，后缀仅 `"A"`。**裁剪只能切出"一段"待定区（中间的 `"AAA"` vs `"BAB"`）,不会在中间再找回一次"相同点"去拆成两段**，所以无法识别出"第 3 位的 A 是一个锚点、后面的 B 是新的改动起点"这种两段式结构。
- 中间区交给现有 `diffChars("AAA", "BAB")`，按 DP 回溯规则实际运行结果为：`del("AA") + add("B") + same("A") + add("B")`。数学上还原正确（旧=`AA+A`，新=`B+A+B`），但展示效果是"整块删两个字、句尾整块插一个字"，而不是人类直觉中"逐位交替替换"（A→B、A不变、A→B）。

**原因**：LCS 只保证"编辑距离最短/公共子序列最长"，不保证"对应关系符合直觉"；重复字符越多，候选公共子序列越多，越容易选中一个数学最优但阅读别扭的解。

**缓解规则（可选优化，非根治）**：在 Step3 调用 `diffChars` 前增加一个前置判断——**若待比较的两段文本长度相等**，改用逐位比较（`a[k]` vs `b[k]`，`k=0..n-1`）代替 LCS，直接得到 same/diff 交替序列，结果确定且更符合直觉，计算量从 O(n·m) 降到 O(n)。

- 长度相等时：`AAA` vs `BAB` 按位比较 → `A/B`（改）`A/A`（同）`A/B`（改），效果符合预期。
- **长度不等时该规则失效**（存在插入/删除会导致后续按位错位，无法简单套用），只能退回现有 LCS 逻辑，接受其可能出现的块状/不直观结果——这是机械规则的固有边界，需要在评审时明确告知，不宜承诺"任何情况都能精确定位"。

#### 3.3.2 反例验证：纯增删场景（长度不等）判定可靠，无需额外规则

**问题场景**：`AAA` → `ACAA`（旧串3 个字符，新串 4 个字符，中间插入了一个 `C`）。同样存在重复字符 `A`，但长度不同，实测按现有 `diffChars` 的 DP 规则逐位回溯：

| 步骤 | 比较 | 判断 | 结果 |
|---|---|---|---|
| 1 | `a[0]='A'` vs `b[0]='A'` | 相等 | same("A") |
| 2 | `a[1]='A'` vs `b[1]='C'` | 不等，`dp[2][1] < dp[1][2]` → 走 add | add("C") |
| 3 | `a[1]='A'` vs `b[2]='A'` | 相等 | same("A") |
| 4 | `a[2]='A'` vs `b[3]='A'` | 相等 | same("A") |

结果：`same("A") + add("C") + same("AA")`，还原校验：旧 = `A+AA`✓，新 = `A+C+AA`✓，且展示效果"A（不变）+C（插入）AA（不变）"完全符合直觉，**没有出现锚点歧义**。

**原理**：旧串里 3 个 `A`、新串里也恰好只有 3 个 `A`（外加 1 个净增的 `C`），LCS 要在新串中找到与旧串等量的 `A` 做对应，数量唯一、顺序唯一，不存在"选哪几个字符当锚点"的多解情况——歧义只在"长度相等、内容重复错位"（如 3.3.1 的等长替换）时才会出现。

**结论**：字段级 diff 中常见的"插入一段话""删除一段话"等纯增删场景，即使原文有重复字符，现有机械规则也能可靠定位，**不需要**额外的按位对齐等特殊处理；3.3.1 的缓解规则只需要在"两侧长度相等"时触发即可。

### 3.4 标准化规则（用于相似度/相等判断）

各级片段比较前都先做一次"标准化"，减少格式噪音：

- 去除首尾空白，连续空白（含全角空格）合并为一个
- 统一全角/半角标点（仅用于比较，不影响原文展示）
- 不做分词处理，保留文字与标点的原始顺序

若两个片段标准化后完全相等但原始文本不等 → 判定为「纯标点/格式差异」，弱化展示，默认不计入"字段变化数"统计（可配置）。

### 3.5 兜底策略

- 任意一级切分后片段数量过多，或单对「修改对」文本过长（超过 `diffChars` 现有的 `n*m` 阈值），跳过更细一级的定位，直接在当前级别整体标记替换，避免性能问题。
- 若 Step 0 裁剪后差异区为空（说明两段文本完全相同），直接返回 `same`，不进入 Step 1~3。
- 若字段原本为空文本，直接走"整体新增/整体删除"逻辑，不经过上述级联流程。

## 四、UI 展示建议

- **一级高亮**：以子句为单位的浅底色色块，区分"新增句""删除句""修改句"
- **二级高亮**：仅在"修改句"内部展示字符级红删除线/绿新增（复用当前 `.diff-del` / `.diff-add` 样式）
- **弱化标记**：纯标点/格式差异用浅灰 Tag 提示，不与实质内容变化混在一起，避免误导审核人员觉得"内容变了"
- **图例说明**：在对比面板头部增加一行提示"差异为机械规则识别，可能与实际编辑意图存在偏差"，避免用户误认为是语义级 AI 分析结果

## 五、本方案不覆盖的部分（明确排除，供评审确认）

- 主动标注"移动到了哪个位置"（3.1 只做到"内容仍存在→不误报增删"，不展示移动路径，因为具体对应哪个位置在重复内容场景下无法确定性判断）
- 语义等价改写判断
- 数字/大小写等格式归一化比较
- 跨句的复杂重排（拆句/合句）优化对齐

以上如后续有需要，需引入分词、编辑距离加权、或 AI 语义比对能力，超出"机械规则"范围，建议作为后续迭代单独评估。
