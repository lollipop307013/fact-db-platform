## 需求 5：操作记录与状态机校验【P0】

### 5.0 业务目标

每一次状态变更、字段编辑都可追溯；非法状态流转必须被阻止或明确告知用户。

> 状态值统一以后端真实取值为准（详见[附录 § 二、字段命名与状态规范](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126457)）。

---

### 5.1 状态机（双轴模型）

事实（Fact）有**两个独立的状态轴**：

#### 5.1.1 review_status（审核状态轴）

```
pending（待审核） ──通过──→ approved（已通过）
       │
       └──拒绝──→ deleted（已拒绝/软删除）
                       │
                       └──撤回──→ pending（重新进入审核）
```

转移规则：

| 起始 | 允许迁移到 |
|---|---|
| pending | approved（通过）、deleted（拒绝） |
| approved | deleted（撤回审核结果，慎用） |
| deleted | pending（撤回拒绝，回到待审核） |

#### 5.1.2 upload_status（同步状态轴，由后端自动维护）

upload_status 表示"事实是否已同步到 RAG/Bot 检索使用"，由**后端自动维护**，前端不可手动操作。详见[子4 同步状态](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126273)。

```
pending（待上传）──自动同步──→ done（已上传）
     │                              │
     │ 内容更新                      │ 同步失败
     └──→ need_update（待更新）      └──→ failed（上传失败，后端自动重试）
                                           │
                                           └──重试成功──→ done
```

**前端无手动操作**：不上线/下线/重试按钮。

#### 5.1.3 实体 / 事件（单轴）

实体 / 事件**只有 review_status，没有 upload_status**——它们的上线由 `/api/upload_entity_event` 全量同步管理，不分单条上下线。

```
pending（待审核） ⇄ approved（已通过）
       │
       └─拒绝/删除─→ deleted（软删除）
```

#### 5.1.4 审核区条目（前端缓冲池，未入库）

审核区条目仅在前端有状态，对应后端尚未持久化：

| 前端状态 | 含义 | 入库后映射 |
|---|---|---|
| 待审核 | 提取出尚未确认 | 不入库（批次必须全审完才能入库） |
| 已通过 | 审核通过 | 入库为 review_status=approved |
| 已拒绝 | 审核拒绝 | 入库为 review_status=deleted（仅记录留痕） |

具体审核交互详见 [1期-子1-提取结果审核工作台 § 1.4 单条事实行](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126280)。

### 5.2 中文展示与后端值对照

| 后端值 | UI 展示 | 颜色 |
|---|---|---|
| review_status=pending | 待审核 | warning（黄） |
| review_status=approved | 已通过 | success（绿） |
| review_status=deleted | 已拒绝 | default（灰） |
| upload_status=pending | 待上传 | default（灰） |
| upload_status=need_update | 待更新 | warning（黄） |
| upload_status=done | 已上传 | success（绿） |
| upload_status=failed | 上传失败 | danger（红） |

> upload_status 四态由后端自动维护，前端仅展示与筛选。详见 [子4](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126273)。

### 5.3 批量操作的状态校验

批量审核 / 批量状态变更时：

- **全部符合** → 直接执行，toast 反馈"已对 N 条执行"
- **部分符合** → 弹确认 Dialog："选中的 N 条中：✅ M 条将变更，⚠ K 条已是目标状态或不满足前置条件，将跳过"
- **全部不符合** → toast 警告"所选记录均不满足条件，无需变更"

典型不满足场景：

| 操作 | 跳过条件 |
|---|---|
| 批量审核通过 | review_status 已是 approved |
| 批量拒绝 | review_status 已是 deleted |

### 5.4 操作记录字段

每个实体 / 事件 / 事实记录都关联一份 logs[]：

| 字段 | 说明 |
|---|---|
| id | 自增 |
| operator | 操作人（登录态注入） |
| time | 操作时间（ISO 字符串） |
| action | 操作类型（见 §5.4.1 操作类型对照表） |
| module | 模块类型（entity / event / fact / category） |
| detail | 详情文案（含字段 diff 摘要，见 §5.4.2 detail 文案规范） |

#### 5.4.1 操作类型对照表

后端 `action` 字段值与前端展示文案对照：

| 后端值 | 前端展示文案 | 适用模块 | 说明 |
|---|---|---|---|
| `create` | 创建 | 全部 | 手动新建 |
| `update` | 编辑 | 全部 | 单条编辑 |
| `delete` | 删除 | 全部 | 单条删除 |
| `batch_delete` | 批量删除 | 全部 | 批量删除 N 条 |
| `batch_update` | 批量更新 | 全部 | 批量更新字段 |
| `batch_review` | 批量审核 | 全部 | 批量通过/拒绝审核 |
| `import` | 导入 | 全部 | CSV 批量导入 |
| `export` | 导出 | 全部 | 导出 CSV |
| `extract` | 事实提取 | 仅 fact | AI 提取生成事实 |

> ⚠️ 以下操作类型后端常量已定义，但**一期未实现**，操作日志不会出现：`merge`（合并）、`contradiction_check`（矛盾检测）、`error_check`（错误表述检测）、`batch_correct`（批量修正）。

#### 5.4.2 操作日志展示文案规范

操作记录列表/弹窗中，每条日志的展示格式：

| 操作类型 | 展示文案示例 |
|---|---|
| `create` | 创建事实 |
| `update` | 修改标题：「旧标题」→「新标题」；修改事实内容 |
| `delete` | 删除事实【[166634] xxx】 |
| `batch_delete` | 批量删除 N 条事实 |
| `batch_update` | 批量更新 N 条事实 |
| `batch_review` | 批量审核 N 条事实：N 条通过，M 条跳过 |
| `import` | 导入事实 N 条，成功 M 条，失败 K 条 |
| `export` | 导出事实 N 条（批次：[BATCH-xxx]） |
| `extract` | 从「文本/文件」提取事实 N 条（批次：[BATCH-xxx]） |

**编辑日志的 detail 格式**：自动 diff 字段差异，例如：

```
修改了：fact_text、entity_ids（+456 弧光玫瑰）、end_time（2026-04-23 → 2026-05-01）
```

> 操作记录的存储 / 接口由后端实现，前端只读展示。一期范围以本 §5.4.1 对照表为准，超出部分后端无需记录。

---

### 5.5 操作记录入口

- **行级日志**：表格行操作列「操作记录」按钮 → 弹 Dialog 展示该条记录的全量历史
- **批量导入日志**：批量导入对话框内独立 Tab（来自子2）
- **首期不做**：跨记录的全局操作记录检索（划入 2 期）

---

### 5.6 与其它模块的关联

- 全模块复用同一套日志结构与展示组件
- 审核区阶段的日志独立（详见 [1期-子1-提取结果审核工作台 § 1.7 操作日志 Dialog](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126280)），入库后转换为事实库的日志（带 action="创建-提取"）
