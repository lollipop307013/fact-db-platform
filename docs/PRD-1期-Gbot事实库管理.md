## 一、项目背景与目标

### 1. 业务背景

- **痛点**：基于大模型的游戏客服与助手存在严重幻觉，回答事实精度无法保证。
- **核心对策**：将松散的业务长文档，通过机器预处理 + 大模型抽取，转化为结构化的"事实（Fact）"，并挂载在游戏的"实体（Entity）"和"事件（Event）"图谱节点上，以高结构化的形式反哺 AI 问答。
- **核心价值**：把"AI 提取 + 人工审核"打造为生产可用的核心生产链路，让业务方可以低门槛、可追溯地批量产出图谱知识。

### 2. 首期目标

| # | 目标 | 衡量 |
|---|---|---|
| 1 | 提取审核流程闭环 | 业务方可在工作台完成 AI 提取 → 逐条审核 → 入库的全流程，平均单条审核耗时 ≤ 30s |
| 2 | 多源批量入库 | 文本粘贴、PDF / Word / Excel / CSV 文件均可作为入口产出候选事实 |
| 3 | 数据治理可追溯 | 实体 / 事件 / 事实每一次状态变更与字段编辑均有完整记录 |
| 4 | 异常可见 | 上线失败、冲突 / 重复事实在列表中可一眼看到并支持快速处理 |
| 5 | 多人协作 | 提取结果共享可见、按提取人筛选；状态机校验防止误操作 |
| 6 | **多游戏隔离** | 顶部游戏切换贯穿所有 Tab，不同游戏数据完全隔离 |
| 7 | **多语言支持** | 实体 / 事件 / 事实的列表 / 编辑 / 导出均支持 6 种语言（zh/en/ar/tr/ru/zh-hk） |

## 二、整体产品架构

### 1. 模块导航

```
内容管理（核心主菜单）
├─ 实体管理        Entity Tab
├─ 事件管理        Event Tab
├─ 事实管理        Fact Tab
├─ 提取结果审核    Extract Tab     ··· 核心工作台
├─ 问题回复        QA Tab
└─ 错误表述检测    Error-Detect

辅助
└─ 操作记录        OperationLog    ··· 行级日志，跨模块复用
```

顶部全局组件：
- **游戏切换下拉**（`/api/games`）：所有接口必带 `parent_game_id`
- **语言切换**：影响列表展示的字段语言（zh / en / ar / tr / ru / zh-hk）
