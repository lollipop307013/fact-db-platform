## 需求 1：提取结果审核工作台【P0】

### 1.0 业务目标

把 AI 提取的事实组织为分批次、可对比、可追溯、状态明确的工作流，是事实库的主进货口。

**整体页面结构**：

左右两栏：
- **左侧（占比 30%）**：提取输入区（可收起）
- **右侧（占比 70%）**：提取结果审核区，按批次组织

**左侧收起/展开**：
- 左右两栏之间有一根细分割线，中间悬浮一个小矩形条（浅灰色，14×48px）
- 点击小条 → 左侧输入区折叠，右侧审核区占满全宽
- 再次点击 → 恢复原始比例
- 收起状态下分割线渐隐；展开时恢复
- 适用场景：提取完成后专注审核，无需再输入文本

### 1.1 提取输入区

| 字段 / 控件 | 说明 |
|---|---|
| 输入方式切换 | 文本粘贴 / 文件上传（详见 [1期-子2-多源批量导入](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126278)） |
| 文本输入框 | 支持多行粘贴，最少 12 行高度，自动展开 |
| 提取模式 | 单段提取（整段 = 1 条事实） / 多段提取（自动拆为多条），每个选项带 ⓘ 解释气泡 |
| 模型选择 | 下拉选择 LLM，由后端配置可用模型列表 |
| 提取按钮 | 点击进入加载态 |
| Loading 文案 | 紧贴按钮下方"提取中，结果将出现在右侧…"，加载完成自动消失 |

**业务规则**：
- 文本为空 → 报错 toast"请输入文本内容"
- 提取完成 → toast"提取完成（{batchId}），生成 N 条事实"
- 提取后清空文本框，便于继续粘贴下一段

### 1.2 审核区顶部

| 元素 | 说明 |
|---|---|
| 标题 | "提取结果审核" |
| ⓘ 帮助图标 | hover 弹层展示完整使用说明（5 步流程 + Tag 含义） |
| 统计 | 共 N 条 · 待审核 N · 已审核 N |
| 范围筛选 | 全部 / 只看自己的（默认"全部"） |
| 入库 / 归档已完全审核批次 | 一键入库当前视图所有「全部审核完毕」批次的已审核条目；按钮文案恒定，存在符合条件的批次时才显示 |

**业务规则**：
- 提取结果团队级共享可见
- 筛选范围切到"只看自己的"时，统计、入库按钮均按筛选后的数据计算

**帮助图标弹层文案**（首期固定文案）：

```
使用说明
AI 提取的事实先进入此处暂存，审核通过后才会入库。所有人共享可见。

使用步骤：
1. 左侧粘贴文本，选择提取模式后点「提取事实」
2. 右侧按批次查看提取结果，逐条核对：
   • 事实内容是否准确
   • 关联实体 / 新发现实体 / 关联事件 / 新发现事件
   • 冲突 / 重复事实提示（点击 Tag 可查看对比）
3. 必要时点「编辑」修改内容（编辑保存后会重新校验冲突）
4. 逐条「通过」/「拒绝」，或整批通过 / 拒绝
5. 批次全部审核完毕（无待审核）后，可点单批次「入库 / 归档批次」按钮，或顶部「入库 / 归档已完全审核批次」一键入库；已审核条目入事实库（默认已审核状态），批次随即归档（archiveReason=committed）
```

### 1.3 批次卡片

每次提取生成一个批次，按时间倒序展示。

**批次字段**：

| 字段 | 说明 |
|---|---|
| batchId | 批次业务编号，规则详见 [附录 - ID 与命名规范](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126457) |
| batchLabel | 自动取来源文本前 40 字 |
| extractedAt | 提取时间 |
| extractor | 提取人（用于追溯 + 筛选） |
| model | 使用的模型 |
| mode | 单段提取 / 多段提取 / 文件解析 |
| facts | 该批次的候选事实数组 |

**批次头展示**：
- 批次编号 Tag（独立显著展示，点击一键复制到剪贴板）
- 批次标题（来源文本前 40 字）
- 副信息：提取时间 · 提取人（自己提取的标"（我）"，品牌色高亮）· 模型 · 模式 · 共 N 条
- 状态徽章：待审核 N / 已审核 N / 已拒绝 N（按数量出现）

**批次头交互**：
- 折叠 / 展开 该批次
- **查看原文 / 查看来源内容**（折叠面板）：
  - 文本粘贴批次：展示用户粘贴的原始文本
  - **CSV 文件导入批次**（v2.2 新增 / mode=csv_extract）：**展示文件名 + 超链 + 下载入口**（不展示文本原文）；点击文件名可下载原始 CSV
  - 其它文件导入批次（后续支持）：展示来源文件名 + 被提取的各片段位置标记和内容；按钮文案改为「查看来源内容」
- **整批通过 / 整批拒绝**（动态文案）：
  - 批次内**无任何审核动作**时显示「整批通过」「整批拒绝」，处理批次内全部待审核条目
  - 批次内**已有部分审核**时显示「剩余全部通过」「剩余全部拒绝」，仅处理剩下的"待审核"条目，已标注的不变
  - 按钮 minWidth 96 防文案切换时位移
- **批次审核完毕**（无待审核）时，整批通过/拒绝按钮自动替换为绿色「入库 / 归档批次」按钮（单批次入库）
- **删除批次**：右侧 × 图标按钮（hover 提示），点击弹出二次确认；批次内含「已审核未入库」条目时弹窗显著红字警告，按钮文案变为"仍要删除"

**批次审核进度条**：
- 位置：批次头底部，紧贴批次头与事实列表之间
- 高度：2px 细线（克制风格，不渲染整片背景）
- 默认蓝色（`var(--td-brand-color)`）填充已审核+已拒绝占比
- 全部审核完毕时整条变绿色（`var(--td-success-color)`）
- hover 显示 Tooltip：「审核进度 N/M（待审核 X）」或「已全部审核（X 通过 / Y 拒绝）」
- 折叠/展开都可见，已归档批次不显示

### 1.4 单条事实行（FactRow）

每个批次内的事实以行卡片展示，结构为三栏：

```
┌──┬─────────────────────┬──────────────────┬──────────┐
│序│ 事实内容（可宽展示）  │ 实体匹配 / 事件匹配 │ 操作区    │
│号│ ⚠ 冲突事实：[ID:xxx] │ + 时间信息         │ 状态徽章  │
│  │ ≈ 重复事实：[ID:xxx] │                  │ 编辑/通过 │
│  │                     │                  │ 拒绝/撤回 │
│  │                     │                  │ 删除/日志 │
└──┴─────────────────────┴──────────────────┴──────────┘
```

#### 1.4.1 左侧 · 事实内容区

- 完整展示事实文本
- **冲突 Tag**：`⚠ 冲突事实：[ID:xxx]`（红色），hover Tooltip 看冲突原因；点击弹"对比 Dialog"
- **重复 Tag**：`≈ 重复事实：[ID:xxx]`（黄色），hover 看相似度+片段；点击弹"对比 Dialog"
- 同时存在冲突与重复时，两个 Tag 并列展示

#### 1.4.2 中间 · 关联信息区

**实体匹配**：
- 已有实体：灰色 Tag，可关闭（关闭即移除关联）
- 建议新增实体：黄色 Tag，文案 `建议新增：xxx · N 标签`，hover 看描述+标签预览，点击 Tag 切换 keep / discard 状态

**事件匹配**：
- 已有事件：灰色 Tag，可关闭
- 建议新增事件：黄色卡片，含名称 / 类型 / 时间 / 描述；右上"丢弃 / 恢复"按钮

**有效时间**（仅当任一字段非空时展示）：
- 开始时间 ~ 结束时间
- 时间描述

#### 1.4.3 右侧 · 操作区

操作按钮按状态显示：

| 当前状态 | 编辑 | 通过 | 拒绝 | 撤回 | 删除 | 日志 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| 🟡 待审核 | ✓ | ✓ | ✓ | — | ✓ | ✓ |
| 🔵 已审核 | ✓（仅改内容） | — | — | ✓（→待审核） | ✗ | ✓ |
| ⚪ 已拒绝 | ✗ | — | — | ✓（→待审核） | ✓ | ✓ |

**关键规则**：
- 已审核 / 已拒绝 状态确定后不可重复横跳；编辑只改内容、不改状态
- 已拒绝可撤回到待审核（缓冲池为临时区，允许反悔）
- 日志按钮带条数 Tooltip："查看操作记录（N 条）"

### 1.5 编辑抽屉（双栏）

打开方式：行内"编辑"按钮 → 右侧 80% 屏宽抽屉（v2.1 起从 60vw 扩为 80vw，承载完整 POST /api/facts 字段集）。

#### 1.5.0 整体结构

抽屉分为左右两栏，比例约 1.2 : 1：

- **左栏「事实主体」**：用户审核时主要看 / 改的内容（多语言切换 + 事实正文 + 时效 + 关联实体/事件 + 新建议）
- **右栏「元数据」**：来源、矛盾、扩展、审核优先级等元信息（4 个分组，组间用底部分割线分隔）

字段密度高时整体仍可滑动，左右栏独立 `overflow:auto`。

#### 1.5.1 左栏 · 事实主体

##### A. 多语言切换（仅影响三个文本字段）

顶部一行 6 个语言按钮（zh/en/ar/tr/ru/zh-hk），按钮组样式 outline，选中态 base 主色。

**切换范围（重要边界）**：仅以下 3 个字段按语言独立保存：
- `fact_text` 事实内容
- `time_description` 时间描述
- `title` 标题（在右栏，但同样响应语言切换）

其它字段（来源、矛盾、扩展 JSON 等）**语言无关**，所有语种共享。

**填充提示**：非当前语种的按钮，若该语种已有任一字段被填充过，按钮右侧加绿点（`•`）提示，方便审核者一眼看出哪些语言已翻译。

**冲突/重复实时校验**：仅在 zh 模式下展示（校验基于中文主字段），切到其它语种时校验提示自动隐藏。

##### B. 事实内容（fact_text）

- 必填，Textarea，autosize minRows=6
- **实时冲突 / 重复提示**（基于当前 content 调后端接口实时校验）：
  - 命中冲突：红框告警 + 冲突 ID Tag + 「查看对比」按钮
  - 命中重复：黄框告警 + 相似度 + 「查看对比」按钮
- **解除提示**：原本有冲突 / 重复，编辑后已不再命中 → 绿框「✓ 编辑后已不再与 [ID:xxx] 冲突，保存即生效」

##### C. 时效（事实级，非事件级）

- 开始时间 `start_time` / 结束时间 `end_time`：DatePicker 并排（flex 1:1）
- 时间描述 `time_description`：Input，多语言响应

##### D. 关联实体 / 事件

| 区块 | 说明 |
|---|---|
| 关联实体（已存在） | 搜索下拉添加，已选项 Tag 可关闭 |
| 新发现实体（待入库） | 卡片表单：名称 / 描述 / 标签（逗号分隔）；头部右上 丢弃 / 恢复 / × 删除；保留时显示绿色 `ID:xxxxx` Tag（reservedEntityId）|
| 关联事件（已存在） | 交互同实体 |
| 新发现事件（待入库） | 卡片表单：名称 / 类型 / 开始时间 / 结束时间 / 时间描述 / 描述 / 标签；保留时显示绿色 `ID:xxxxx` Tag（reservedEventId）|

每个区块底部都有「+ 添加新实体 / 新事件」按钮，让审核者补充 AI 漏抽的内容。

#### 1.5.2 右栏 · 元数据

分 4 个分组，每组顶部有一行小标题（深灰、12px、底边线）：

##### A. 基础信息

| 字段 | 类型 | 多语言 | 说明 |
|---|---|---|---|
| `title` 标题 | Input | ✅ | 事实标题，可选 |
| `category_id` 分类 | Select | - | 关联分类树（首期 mock 简单枚举：无分类/活动/技能/皮肤/玩法/其他）|
| `review_priority` 审核优先级 | Select | - | low / medium / high，默认 low |

分类与审核优先级并排（flex 1:1）。

##### B. 来源溯源

| 字段 | 类型 | 多语言 | 说明 |
|---|---|---|---|
| `source_type` 来源类型 | Input（**只读**） | - | 系统字段，从提取结果带过来不可改：extract_text / extract_doc / extract_csv / manual / api_import |
| `source` 来源 | Input | - | 提取人 / 手动来源 |
| `source_url` 来源 URL | Input | - | https:// 开头，原始 URL |
| `source_content` 来源内容 | Textarea | - | 原始问答对 / 批次 ID 等可追溯的原文 |

来源类型 + 来源并排（flex 1:1）。

##### C. 矛盾与重复

| 字段 | 类型 | 说明 |
|---|---|---|
| `contradiction_reason` 矛盾原因 | Textarea | 该事实与其他事实存在矛盾时填写；留空表示无矛盾 |
| `contradicting_fact_ids` 矛盾事实 ID | Input | 多个用逗号分隔，如 `1,2,3` |
| `duplicate_fact_ids` 语义重复事实 ID | Input | 同上 |

> 这一组与左栏的"实时冲突/重复提示"是**两套并行机制**：左栏是系统检测的展示，右栏是用户手动登记。后端接受用户登记的 ID 优先于系统检测结果。

##### D. 扩展

| 字段 | 类型 | 说明 |
|---|---|---|
| `extra` 扩展内容 | Textarea | 自由格式 JSON 字符串，如 `{"ticket_id":"12345"}` |

**JSON 校验规则**：
- 非空时必须是合法 JSON
- 校验失败：FormItem 红框 + tips 显示具体解析错误，**保存按钮被拦截**（前端 toast 错误，不发请求）
- 空字符串视为无扩展，不校验

#### 1.5.3 保存逻辑

1. 校验扩展 JSON：失败时 toast 错误并 return，不调保存
2. 触发"重新查冲突"：基于最新 content 调后端校验接口
3. 把校验结果（conflict / duplicate）写回审核区条目
4. 自动生成编辑摘要：`修改了：事实内容、标题、关联实体、已解除与 [ID:42010] 的重复`，写入操作日志
5. Toast 提示"已保存"；若有冲突 / 重复解除，额外 toast「冲突已通过编辑解除」

#### 1.5.4 业务规则

- 抽屉首次打开（visible 从 false 变 true）才重置编辑态，避免编辑过程中被外部数据覆盖
- 已拒绝状态不允许打开编辑抽屉
- 多语言字段未填充时不强制要求；保存时仅传非空语种的字段到 i18n 对象（前端组装 `entity_name_en/ar/tr/ru/zh_hk` 等参数）
- 来源类型不可编辑：保留系统提取来源，避免混淆数据治理

#### 1.5.5 字段汇总（与 POST /api/facts 接口对照）

便于开发评审一眼看清楚字段映射：

| UI 字段 | 后端字段 | 必填 | 多语言 | 编辑性 |
|---|---|---|---|---|
| 事实内容 | fact_text | ✅ | ✅ | 可编辑 |
| 时间描述 | time_description | - | ✅ | 可编辑 |
| 标题 | title | - | ✅ | 可编辑 |
| 开始/结束时间 | start_time / end_time | - | - | 可编辑 |
| 关联实体 ID 列表 | entity_ids[] | - | - | 可编辑 |
| 关联事件 ID 列表 | event_ids[] | - | - | 可编辑 |
| 分类 | category_id | - | - | 可编辑 |
| 审核优先级 | review_priority | - | - | 可编辑（默认 low）|
| 来源类型 | source_type | - | - | **只读** |
| 来源 | source | - | - | 可编辑 |

### 1.6 冲突 / 重复对比 Dialog

打开方式：点击行内冲突 / 重复 Tag，或抽屉里「查看对比」。

**结构**：
1. **顶部详情区**（彩色背景）：
   - 冲突：⚠ Tag + 已有事实 ID + 冲突原因文字
   - 重复：≈ Tag + 已有事实 ID + 相似度（"86%"）
2. **中部双栏对比**：
   - 左：已有事实 [ID:xxx] 内容
   - 右：新事实内容
3. **底部差异高亮**：
   - 字符级或词级 diff（颗粒度由实现方决定）
   - 删除部分：红色删除线 + 红底
   - 新增部分：绿色 + 绿底
   - 头部图例提示

**业务规则**：
- diff 算法以可读为先
- Dialog 关闭只关闭，不影响事实数据

### 1.7 操作日志 Dialog

打开方式：行内"日志"按钮。

**结构**：
- 顶部：当前事实标题（前 30 字）
- 列表：每条日志一行
  - 动作 Tag（彩色，按 action 分色）
  - 详情文字
  - 操作人 · 时间

**记录的 action 枚举**：

| Action | 触发时机 |
|---|---|
| 创建 | AI 提取入审核区 |
| 编辑 | 抽屉保存（含字段 diff 摘要） |
| 通过 | 单条 / 整批通过 |
| 拒绝 | 单条 / 整批拒绝 |
| 撤回 | 已审核 / 已拒绝 撤回到待审核 |
| 实体丢弃 / 实体恢复 | 行内或抽屉里切换 keep / discard |
| 事件丢弃 / 事件恢复 | 同上 |
| 冲突解除 | 编辑保存后冲突不再命中 |
| 重复解除 | 编辑保存后重复不再命中 |

**业务规则**：
- 日志倒序展示（最新在最上）
- 日志只追加，不允许删除 / 修改

### 1.8 批量入库

**入口**：
- 顶部「入库 / 归档已完全审核批次」按钮（一键处理所有符合条件的批次）
- 单个批次的「入库 / 归档批次」按钮（在批次全部审核完毕后出现，仅入本批次）

**强校验**：批次内必须**全部条目已标注（无待审核）**才能入库。

| 批次状态 | 顶部按钮 | 单批次按钮 |
|---|---|---|
| 仍有待审核 | 不计入 commitable，按钮可能仍可见但点击会被 toast 拦截：「N 个批次仍有待审核条目，请审核完毕后再入库」 | 不显示 |
| 全部审核完毕 | 计入 commitable | 显示「入库 / 归档批次」 |

**流程**：
1. 弹确认对话框：列出涉及的批次数、已审核条目数（入库）、已拒绝条目数（留痕不入库）
2. 确认后：
   - 在事实库创建对应记录，初始状态 = "已审核"
   - 把所属批次置为已归档（archiveReason: committed）
   - 携带 source 信息（详见 [附录 - 数据来源标记](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126457)）
3. Toast "N 条事实已入库，X 个批次已归档"

**业务规则**：
- 已审核 → 入库后**直接以「已审核」状态进入事实库**，不进行二次审核（审核区审核 = 唯一审核）
- 入库时所属批次自动归档（archiveReason: committed）到「已归档」区
- **committed 批次不可恢复**：缓冲池保留只读快照供溯源，如需修改请到事实库操作（避免缓冲池/事实库双副本不一致）
- 范围切到"只看自己的"时，仅入库本人提取的"已审核"，不影响他人

### 1.9 待处理 / 已归档分区

审核区顶部加二级 Tab：

| Tab | 含义 | 包含批次 |
|---|---|---|
| 待处理 | 仍在工作流中的批次 | archived = false |
| 已归档 | 已完结的批次（导出 / 入库） | archived = true |

**字段定义**：批次新增以下字段

| 字段 | 类型 | 说明 |
|---|---|---|
| archived | boolean | 是否已归档 |
| archiveReason | "exported" / "committed" | 归档原因（手动归档已移除） |
| archivedAt | string | 归档时间 |
| archivedBy | string | 归档操作人 |
| exportedAt | string | 导出时间（archiveReason=exported 时记录） |

**自动归档触发**（两条路径，规则一致：批次内必须无待审核条目才归档）：
- **入库**：批次全审完点入库 → archiveReason = committed；不可恢复
- **导出 Excel**：批次全审完时一并归档 → archiveReason = exported；可恢复
- **不支持手动归档**

**归档后行为分两类**：

| 归档原因 | 已入库 | 可恢复审核 | 可再次导出 | 说明 |
|---|---|---|---|---|
| committed | ✅ | ❌ | ✅（作为只读快照） | 已落入事实库，缓冲池保留只读快照避免双副本不一致；显示「🔒 已入库不可恢复」标签 |
| exported | ❌ | ✅ | ✅ | 仅副本流出，外部审核如有变故可"恢复审核"返回待处理区重审 |

**已归档批次内的事实展示**：
- 默认**隐藏「已拒绝」条目**（数据保留作训练资产，但视觉清爽）
- 底部提供"显示已拒绝（N）"开关，按需切换可见
- 事实行只读：编辑按钮变"查看"、隐藏多选 / 通过 / 拒绝 / 撤回 / 删除

**视觉**：
- Tab 显示数量徽章：`待处理 (N) · 已归档 (M)`
- 已归档批次头加状态 Tag：📎 已导出 / 📥 已入库
- 已归档批次头右侧操作：
  - committed：仅显示「🔒 已入库不可恢复」标签 + 「导出」按钮（导出只读快照）
  - exported：显示「恢复审核」按钮 + 「导出」按钮

### 1.11 导出为 CSV（当前前端实现）

**入口**：多选事实后 → 批量操作栏「导出为 CSV」按钮

**核心限制**：

> 后台不支持把一个批次拆成两部分导出/归档（例如"一半保持待审核，一半导出归档"）。因此导出时**必须选择整个批次的数据**。

#### 1.11.1 导出前校验

点击「导出为 CSV」时，前端校验每个涉及批次是否被完整选中：

- 若某个批次只选了部分事实 → 拦截导出，toast 提示：
  > 只允许导出整个批次的数据，请勾选批次内全部事实后再导出
- 若所有涉及批次都完整选中 → 允许导出

> 提示文案只说明规则，不展示"还有多少条未勾选"，避免把用户引导到手动补数量的复杂操作里。

#### 1.11.2 导出范围

#### 1.11.3 多批次合并

- 支持选择多个完整批次

- **不加 batch_id 列**（后台不关心，入库后也不会带批次标识）

#### 1.11.4 导出字段

### 1.13 新实体 / 新事件确认流程（v2.0 新增）

> 相对 v1.x 重大调整：原有"导出文件 + tmp_id 跨批次去重"方案不再使用。**新实体 / 新事件的去重由后端 `entities/recall` 在提取阶段保证**，前端在审核环节直接调用真实接口确认。

#### 设计原则

1. AI 提取阶段：自动调 `POST /api/facts/extract` → 后端通过 `/api/entities/recall` 已经把所有"已存在的实体"匹配为正式 entity_id；剩下的才是真正的"新建议实体"
2. 审核阶段：审核者对每个"新建议实体"做决策（保留 / 丢弃 / 编辑后保留）
3. **保留**时：前端立即调 `POST /api/entities` 创建实体，拿到正式 entity_id，写入事实的 entity_ids[]
4. 入库时：事实的 entity_ids[] 已是纯正式 ID 数组，无需再做名称聚合

#### 审核区交互

每条提取事实展开后，新实体卡片有三种决策：

| 决策 | 操作 | 接口动作 | 结果 |
|---|---|---|---|
| 保留（默认） | 保持当前状态 | 审核通过时调 `POST /api/entities` 创建（review_status=pending）| 拿到 entity_id，加入事实 entity_ids[] |
| 编辑后保留 | 点击实体卡 → 编辑名称/描述/标签 | 同上，但用编辑后的字段 | 同上 |
| 丢弃 | 点击 × 置灰划线 | 不创建实体 | 不加入事实 entity_ids[] |

#### 跨批次同名处理（已被前置）

由于 entities/recall 已经做名称匹配，**同名场景应该在提取阶段就被定位为"已存在实体"**，不会重复进入"新建议"。极端情况下（如召回服务漏判）若仍有同名建议，由审核者人工合并：

- 审核者发现两个批次都建议"提示音"时，可在事件管理页用合并工具（`POST /api/entities/merge`）事后合并

#### 不允许导出的场景

批次内若存在以下任一情况，"导出为 Excel" 按钮 disabled：

- 有"新建议实体/事件"未做决策（既未保留也未丢弃）
- 有事实的 entity_ids[] 包含未确认的临时引用

提示文案："请先在平台内完成新实体确认后再导出"

### 1.16 异步提取任务的占位卡片与轮询（v2.1 新增）

> 关联：[5/13 评审会议纪要](../docs/2026-05-13-评审会议纪要.md) 决策 4；[1期-子2-多源批量导入](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126278) §2.x

由于 LLM 抽取耗时较长（通常 5～60s 不等），文件导入 / 长文本提取走**异步任务**，不阻塞 UI。审核区**不引入独立任务列表页**，而是用"占位卡片"在原批次卡片体系内承载任务态。

#### 1.16.1 触发场景

| 场景 | 同步 / 异步 |
|---|---|
| 文本粘贴 → 提取（短文本，< 500 字） | 同步：直接生成批次卡片展示结果 |
| 文本粘贴 → 提取（长文本） | 异步：生成占位卡片 → 轮询 → 转为正式批次卡片 |
| **CSV 文件导入** → 提取（事实抽取批次模板）| **始终异步**：文件由后端解析+逐行抽取，前端只上传+轮询；批次卡片"查看原文"显示文件名+超链+下载（不展示文本）|

> 同步/异步的判断由后端响应决定（同步直接返回 `data.facts[]`；异步返回 `task_id` + `status=pending`），前端不需自己判断长度阈值。

#### 1.16.2 占位卡片状态机

占位卡片是审核区"批次卡片"的特殊形态，外观上保持与正式批次卡片一致的位置、宽度、边距，但内容显示任务进度而非提取结果。

```
       上传成功                  收到 status=running       任务完成（status=success）
START ──────────► [pending] ────────────────► [running] ─────────────► [success]
                     │ 5s 内首次轮询拿到状态        │
                     │                              │ 任务失败（status=failed）
                     │                              ├───────────────► [failed]
                     │                              │
                     │ 用户取消                     │ 用户取消
                     ├──────────► [cancelled]       └──────► [cancelled]
                     │
                     │ 30s 仍未拿到首次响应
                     └──────────► [timeout]
```

每个状态对应不同的卡片视觉：

| 状态 | 头部 Tag | 进度条 | 副标题 | 操作按钮 |
|---|---|---|---|---|
| pending | `📥 已提交` 灰色 | 不显示 | "等待后端开始处理…" | 取消 |
| running | `⏳ 提取中` 蓝色 | 显示（可不准，分阶段：解析 / 抽取实体 / 抽取事件 / 入临时库） | "已处理 N/M 行" | 取消 |
| success | （转为正式批次卡片） | - | - | - |
| failed | `✗ 失败` 红色 | 不显示 | 错误信息（最多 2 行）| 重试 / 删除 |
| cancelled | `⊘ 已取消` 灰色 | - | "用户主动取消" | 删除 |
| timeout | `⚠ 超时` 黄色 | - | "任务长时间未响应，请联系管理员" | 重试 / 删除 |

success 时卡片**就地转换**为正式批次卡片（不闪屏、不重新插入位置），头部 Tag 渐变为正式批次 Tag。

#### 1.16.3 轮询策略

由前端发起，**每张占位卡片独立轮询**（互不影响）：

| 阶段 | 轮询间隔 | 上限 |
|---|---|---|
| 上传成功 → 首次状态返回 | 1s 一次（含立即轮询）| 最多 30s（30 次），仍 pending → 进入 timeout |
| running 阶段 | 3s 一次 | 无上限，直到 success / failed / cancelled |
| failed / cancelled / timeout | 不轮询 | - |

**网络异常容忍**：连续 3 次轮询失败 → 卡片显示警告条「网络异常，已暂停轮询，10s 后自动恢复」，10s 后恢复。**不直接判 failed**（后端任务可能仍在跑）。

**页面切换时不停轮询**：用户切到其它 Tab 不暂停（让任务完成后能立即看到，而不是用户回来才发现还在转）。

#### 1.16.4 并发限制

同一用户在审核区**最多同时存在 5 张占位卡片**（pending+running 计），超过时上传/提取按钮 disabled，提示"已有 5 个任务进行中，请等待至少一个完成"。

> 该限制只在前端拦截；后端是否限流由后端自行决定。这个数字 5 后续可调，写在前端常量。

#### 1.16.5 失败兜底

| 失败类型 | 处理 |
|---|---|
| 后端返回 status=failed + error_msg | 卡片显示错误信息；提供「重试」按钮（重新调原 extract 接口）|
| 轮询连续 30s 未获 status | 进入 timeout 态；提供「重试」按钮 |
| 用户主动取消 | 卡片转 cancelled；后端任务尽力而为停掉（调取消接口若有）|
| 部分行抽取失败（如 CSV 100 行有 5 行解析失败）| status=success 但卡片头部加 `⚠ 5 行异常` Tag，点击可展开异常行原文 + 错误原因 |

#### 1.16.6 占位卡片**不进入**已归档区

- 占位卡片状态不属于审核流程的"已审核/已拒绝"范畴，归档逻辑不适用
- success 转为正式批次卡片后才走归档逻辑
- failed / cancelled / timeout 的卡片由用户手动「删除」清理，不自动归档

#### 1.16.7 后端依赖（与开发对齐）

需要后端提供：

| 接口 | 用途 | 状态 |
|---|---|---|
| `POST /xiaoyue-operation/facts/extract`（异步模式）| 长文本提取，返回 task_id | ❓ 现有接口需补异步语义 |
| `POST /xiaoyue-operation/import/upload-csv`（暂定）| CSV 文件上传 + 触发解析 | ❌ 待补 |
| `GET  /xiaoyue-operation/tasks/{task_id}/status`（暂定）| 任务状态查询 | ❌ 待补 |
| `POST /xiaoyue-operation/tasks/{task_id}/cancel`（暂定）| 任务取消 | ❌ 可选，没有时退化为前端不做实质取消 |

> 这几个路径是 PRD 占位描述，真实路径以开发实现为准；最关键的是**任务状态查询**，没有这个轮询无法实现。
