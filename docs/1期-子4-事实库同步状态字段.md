## 需求 4：事实库同步状态字段【P1】

### 4.0 业务目标

事实有两个独立状态轴：

1. **review_status**（审核状态）：pending / approved / deleted（详见[子5 状态机](https://tapd.woa.com/tapd_fe/10153191/story/detail/1010153191134126267)）
2. **upload_status**（同步状态）：审核通过的事实是否已被后端自动同步到 RAG/Bot 检索使用

> upload_status 由**后端自动维护**，不接受前端写入。前端职责：列表展示当前状态 + 暴露失败汇总入口便于发现异常。

---

### 4.1 字段定义

事实数据结构（来自 `/api/facts`）：

| 字段（后端） | 类型 | 含义 |
|---|---|---|
| review_status | enum | pending / approved / deleted |
| upload_status | enum | pending / need_update / done / failed |

#### upload_status 取值映射（后端 yandongchen 5/22 确认）

| 后端值 | 中文展示 | 含义 |
|---|---|---|
| `pending` | 待上传 | 还没上传过（首次入库后默认值）|
| `need_update` | 待更新 | 已上传过但事实内容更新过，需要重新同步 |
| `done` | 已上传 | 当前已成功同步到 RAG/Bot |
| `failed` | 上传失败 | 同步过程中失败（含异常监测）|

---

### 4.2 列表展示（Fact Tab 新增"同步状态"列）

| upload_status | 视觉 | hover 提示 |
|---|---|---|
| done | success（绿）Tag「已上传」 | "当前已同步到 RAG/Bot，外部可检索" |
| pending | default（灰）Tag「待上传」 | "等待后端自动同步，通常数秒内完成" |
| need_update | warning（黄）Tag「待更新」 | "事实内容已更新，等待重新同步" |
| failed | danger（红）Tag「⚠ 上传失败」 | "同步失败，请联系管理员；后端会自动重试" |

**表头**：带 ⓘ 提示，hover 解释四态含义和"由后端自动维护"。

**筛选**：列表筛选支持按 upload_status 过滤（`/api/facts?upload_status=failed` 等）。

---

### 4.3 异常汇总（v2.1 新增）

> 5/22 决策：批次大时单条 Tag 不易发现失败条目，顶部加汇总入口。

#### 入口位置

事实管理 Tab 列表顶部、Tab 标题与筛选栏之间，固定一行汇总条：

```
┌────────────────────────────────────────────────────────────┐
│  📊 同步状态：✅ 已上传 1240   ⏳ 待上传 32   🔄 待更新 18   ⚠ 失败 5   │
│                                                  [查看失败 →]  │
└────────────────────────────────────────────────────────────┘
```

#### 数据来源

调用 `GET /api/facts/stats` 接口，返回结构（5/22 yandongchen 5/22 同步）：

```json
{
  "review_status": { "pending": 50, "approved": 1280, "deleted": 12 },
  "upload_status": { "pending": 32, "need_update": 18, "done": 1240, "failed": 5 },
  "total": 1342
}
```

#### 「查看失败」按钮

点击 → 自动设置筛选条件 `upload_status=failed`，列表只展示失败条目。

#### 显示规则

- failed > 0 时该数字红字凸显
- failed = 0 时灰字常态展示，不刺激
- need_update > 0 时数字黄字凸显
- 汇总条**始终显示**（即使全部 done 也保持，便于运营对总数有感知）

---

### 4.4 业务规则

- **同步全自动**：upload_status 由后端自动维护，**前端不提供手动上传/重试按钮**
- **审核与同步独立**：review_status=approved 是同步的前提；review_status=deleted 的事实不进入同步流程
- **同步过程透明**：用户编辑事实保存后，upload_status 立即变为 `need_update`，后端检测到后重新同步并最终回到 `done`
- **failed 后续处理**：后端会自动重试；如长时间停留 failed 由运营线下报后端排查

---

### 4.5 不做的功能（v2.1 重新明确）

| 项 | 原因 |
|---|---|
| 单条上线/下线按钮 | upload_status 由后端自动维护，无手动决策语义 |
| 批量上线/批量下线 | 同上 |
| 重试上传按钮 | 后端自动重试 |
| 实体/事件的同步状态展示 | 实体/事件首期不引入 upload_status |

---

### 4.6 与其它模块的关联

- 仅在事实管理（Fact Tab）展示
- 子1 提取审核入库后的事实默认 upload_status=pending；后端自动接管同步
- 子3 编辑事实保存后 upload_status → need_update，触发重新同步
- 子5 状态机不再含上线/下线分支（双轴模型简化为 review 主线 + upload 自动化辅助线）
